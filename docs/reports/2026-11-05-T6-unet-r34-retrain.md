## In plain words
เทรน U-Net ใหม่ด้วย config ปัจจุบัน (เลือก `best.pt` จากค่าเฉลี่ย mIoU ของ 3 ชุดข้อมูล และตั้ง seed ก่อนสร้างโมเดล) ครบ 40,000 iteration

## การตีความ
- **สองรันที่ config เหมือนกันให้ผลต่างกันประมาณ 0.01** (val เฉลี่ย −0.0129, test เฉลี่ย −0.0096) ความต่างนี้อาจมาจาก seed แต่ยังไม่ได้ทดสอบ
  ข้อมูลมีแค่ 2 รัน และการคำนวณบน GPU ไม่ deterministic เต็มที่ จึงยังแยกผลของ seed ออกจากความไม่ deterministic ไม่ได้
- **ความต่างเกือบทั้งหมดอยู่ที่ `accessory`** ถ้าไม่นับคลาสนี้ test ต่างกันแค่ 0.0008 การเทียบ 11 คลาสจึงเสถียรระหว่าง seed ส่วน `accessory` ไม่เสถียร
- **`accessory` เริ่มเรียนช้า และช้าแค่ไหนขึ้นกับ seed** run ใหม่เริ่มช้ากว่า run เดิมหลายพัน step และยังไม่เริ่มเลยบน DFMM ตอน lr ลดถึง 0
- **ที่ 40k ยังไม่อิ่มตัว แต่ขึ้นช้าลง** และส่วนหนึ่งของการขึ้นช่วงท้ายมาจาก lr ที่ลดลงจนเป็น 0

## ข้อโต้แย้ง
ส่วนนี้แย้งคำแนะนำ 40k ของตัวเอง แล้วชั่งน้ำหนักใหม่

### เหตุผลที่ดีที่สุดที่ควรเลือก 80k
**ที่ 40k ผลการเทียบ 3 โมเดลอาจขึ้นกับว่าโมเดลไหน "เริ่มเรียน `accessory` ทันก่อนจบ" ไม่ใช่ว่าโมเดลไหนดีกว่า**

1. ข้อมูลรอบนี้แสดงว่า `accessory` เริ่มเรียนช้า และยังอยู่ช่วงเพิ่งเริ่มตอน 40k (run ใหม่ LIP val 0.0291, DFMM 0.0000)
   ก่อนหน้านี้ผมเขียนว่าปัญหาคือ accessory ไม่ใช่จำนวน step ข้อนี้ไม่ถูกทั้งหมด ข้อมูลบอกว่าปัญหาส่วนหนึ่งคือเวลา: คลาสนี้เรียนได้ แต่ต้องใช้ step มาก
2. คลาสเดียวนี้ทำให้ mIoU เฉลี่ยของสองรันที่ config เดียวกันต่างกันประมาณ 0.01 ถ้า T7 หรือ T8 ห่างจาก U-Net แค่ระดับนี้ เราจะแยกไม่ออกว่าเป็นความต่างของโมเดลหรือของจังหวะการเรียน `accessory`
3. D5 ล็อกจำนวน iteration ให้เท่ากัน ถ้า budget น้อยไป การเทียบจะได้เปรียบโมเดลที่ converge เร็ว
   ในงานทั่วไป SegFormer มักเทรนด้วย schedule ยาวกว่า (เช่น 80k–160k ใน benchmark segmentation ที่นิยมใช้) ข้อนี้เป็นความรู้ทั่วไป ไม่ได้วัดในโปรเจกต์นี้
4. **ตอนนี้เปลี่ยนได้ถูกที่สุด** T7 และ T8 ยังเป็น `todo` ถ้าเปลี่ยนตอนนี้ ต้องเทรนใหม่แค่ U-Net 1 รัน (ประมาณ 2 เท่าของ 73 นาที คือประมาณ 2.4 ชั่วโมง)
   ถ้าเปลี่ยนหลัง T7/T8 เทรนแล้ว ต้องเทรนใหม่ทั้ง 3 โมเดล
5. val และ train loss ยังลดหรือขึ้นอยู่ตอนจบ และ `best.pt` เป็น step สุดท้ายทั้งสองรัน

### เหตุผลที่ยังหนักแน่นสำหรับ 40k
1. **80k ไม่แก้ความแกว่งจาก seed** ถ้าเทรน 80k รันเดียวแล้วดีขึ้นน้อยกว่าประมาณ 0.013 ก็แยกไม่ออกจากความต่างระหว่างสองรันที่วัดได้รอบนี้
   (0.013 คือส่วนต่างของ val mIoU เฉลี่ย 3 ชุดที่ step 40000 = −0.0129 ส่วนต่างของ test mIoU เฉลี่ย 12 คลาสคือ 0.0096 เป็นคนละตัวเลข)
2. **การขึ้นช่วงท้ายส่วนหนึ่งมาจาก lr ลดลงเป็น 0** schedule 80k ไม่ใช่การต่อเส้นกราฟนี้ออกไป จึงเดาผลที่ 80k จากกราฟนี้ไม่ได้
3. **ไม่นับ `accessory` ผลเสถียรแล้ว** test 11 คลาสต่างกันแค่ 0.0008 ระหว่างสอง seed การเทียบโมเดลบน 11 คลาสที่ 40k จึงน่าเชื่อถือ
4. **`accessory` มีทางแก้ที่ตรงจุดกว่า** เช่น E3 (CE + Dice) หรือการให้น้ำหนักคลาส 80k อาจช่วยหรือไม่ช่วยก็ได้ ยังไม่มีหลักฐาน
5. **ต้นทุนเพิ่มกับทุกการทดลองต่อจากนี้** ทุก run ใช้เวลา GPU ประมาณ 2 เท่า รวมถึง E3 และการรันซ้ำด้วย seed อื่น

### ชั่งน้ำหนักแล้ว
ยังแนะนำ **40k แต่น้ำหนักน้อยลงกว่าเดิม และมีเงื่อนไข**:

- รายงาน test mIoU แบบ 11 คลาส (ไม่นับ `accessory`) คู่กับ 12 คลาสเสมอ และรายงาน `accessory` แยก ทำได้จาก `metrics.json` ที่มีอยู่ ไม่ต้องรันใหม่
- ถือว่าความต่างระหว่างโมเดลที่น้อยกว่าประมาณ 0.013 แยกไม่ออกจากความต่างระหว่างรัน
  0.013 มาจากส่วนต่างของ val mIoU เฉลี่ย 3 ชุด (−0.0129) ถ้าเทียบด้วย test mIoU 12 คลาส ส่วนต่างที่วัดได้คือ 0.0096
- **เปลี่ยนเป็น 80k** ถ้าทีมถือว่า `accessory` เป็นผลหลักของงาน (งานเน้นเสื้อผ้าและเครื่องประดับ) เพราะที่ 40k คลาสนี้วัดไม่ได้อย่างเสถียร
  และควรตัดสินก่อน T7/T8 เทรน เพราะหลังจากนั้นต้นทุนจะเป็น 3 เท่า

ถ้าทีมยังตัดสินไม่ได้ ทางที่ได้ข้อมูลมากที่สุดคือเทรน U-Net 80k 1 รันก่อน T7/T8 (ประมาณ 2.4 ชั่วโมง) ถ้าเลือก 80k รันนี้ใช้เป็นผลของ U-Net ได้เลย ถ้าไม่เลือกก็เสียเวลาแค่รันเดียว

## สิ่งที่ยังไม่รู้
- ความแกว่งระหว่าง seed วัดจากแค่ 2 รัน และ run เดิมไม่ได้ตั้ง seed ตอนสร้างโมเดล ตัวเลข 0.01 จึงเป็นแค่ตัวอย่างเดียว
- ไม่รู้ว่า 80k ให้ผลเท่าไร และไม่รู้ว่าจะทำให้ `accessory` เรียนได้สม่ำเสมอขึ้นหรือไม่
- val รายชุดของ run เดิมมีแค่ที่ 40k (ไม่ได้เก็บ checkpoint ระหว่างทาง) เส้น val รายชุดจึงเทียบได้แค่ของ run ใหม่
- ไม่รู้แน่ว่าทำไม `accessory` บน DFMM ถูกทายเป็น `face` มาก (55.6% ของพิกเซล accessory ใน run ใหม่) น่าจะเป็นแว่นตา แต่ยังไม่ได้ดูภาพ
  ไม่ใช่ต่างหู เพราะ `earrings` ของ DFMM ถูก map เป็น IGNORE (`labels.py`) จึงไม่อยู่ในคลาส `accessory`
  จาก scan ดิบ (`data/eda/scan_dfmm.csv`) `eyeglass` อยู่ใน 527 ภาพ ส่วน `neckwear` อยู่ใน 48 ภาพ
