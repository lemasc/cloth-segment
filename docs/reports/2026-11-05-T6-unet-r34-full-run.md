## การตีความ

สิ่งที่ข้อมูลรองรับ:

- **ยังไม่ถึงจุดอิ่มตัว** mIoU เพิ่มทุก check ตลอดการเทรน ช่วงท้ายเพิ่มช้าลง (+0.0031 ที่ 36k, +0.0064 ที่ 40k)
  แต่ไม่ได้แบน หมายเหตุ learning rate ลดเหลือ 0 ที่ step สุดท้าย ส่วนหนึ่งของการขึ้นช่วงท้ายอาจมาจากตัว schedule
  เราไม่ได้ทดสอบว่าถ้าเทรนนานกว่านี้จะดีขึ้นเท่าไร และ D5 ล็อกจำนวน iteration ไว้เท่ากันทุกโมเดล
- **`accessory` อ่อนที่สุดอย่างชัดเจน** IoU 0.107 และเป็นคลาสที่มีพิกเซลน้อยที่สุดใน val (0.12%)
  แต่ขนาดอย่างเดียวอธิบายไม่ครบ เพราะ `skirt` (0.40%) และ `headwear` (0.32%) เล็กใกล้เคียงกันแต่ได้ IoU 0.60 และ 0.67
  แปลว่า `accessory` ยากด้วยเหตุอื่นด้วย (เช่น รูปร่างหลากหลายหรือนิยามคลาสกว้าง) ข้อนี้เป็นสมมติฐาน ยังไม่ได้ตรวจ
- `outer` (0.63) และ `skirt` (0.60) ต่ำกว่าคลาสเสื้อผ้าอื่นอย่าง `pants` (0.82) หรือ `upper` (0.74)

สิ่งที่ **ยังไม่รู้** (ไม่ได้ตรวจในรอบนี้):

- ยังไม่ได้อ่าน confusion matrix จึงไม่รู้ว่า `outer` / `skirt` / `dress` สับสนกับคลาสไหน (เดาว่ากับ `upper` / `dress` แต่เป็นแค่การเดา)
  ข้อมูลมีอยู่แล้วใน `metrics.json` ของแต่ละ test set งานนี้อยู่ใน T9 / T10
- ไม่ได้วิเคราะห์ว่าทำไม LIP และ CIHP ต่ำกว่า DFMM มาก (ความต่างของ domain, ความยากของภาพ หรือป้ายกำกับ)
- รันครั้งเดียว seed เดียว ไม่ได้รันซ้ำ จึงไม่รู้ความแกว่งของ mIoU และไม่รู้ว่ารันซ้ำแล้วได้ค่าเท่าเดิมหรือไม่
  (การคำนวณบน GPU ไม่ deterministic เต็มที่ จึงอาจต่างเล็กน้อย แต่เราไม่ได้วัด)
- learning rate (1e-4) ยังไม่ได้จูน เป็นค่า default ที่ใช้ร่วมกันทุกโมเดล
- ตัวเลขนี้ยังเทียบกับ DeepLabV3+ และ SegFormer ไม่ได้จนกว่า T7 และ T8 จะรันด้วย config ร่วมเดียวกัน
  และการเทียบต้องรายงานจำนวนพารามิเตอร์คู่กัน (D5)

## ข้อจำกัดของการรัน

- **การสุ่มค่าเริ่มต้นของโมเดลไม่ได้ใช้ seed:** `train.run` เรียก `build_model` (`train.py:236`)
  ก่อนที่ `fit` จะตั้ง `torch.manual_seed` (`train.py:139`) ค่าเริ่มต้นแบบสุ่มของ decoder และ head
  (ประมาณ 3.15 ล้านพารามิเตอร์) จึงไม่ได้มาจาก `seed: 0` ส่วน encoder (weight ImageNet) ลำดับข้อมูล
  และ augmentation ใช้ seed ตามปกติ ผลของ run นี้ยังใช้ได้ (เป็นการสุ่มค่าเริ่มต้นปกติ 1 ครั้ง)
  แต่รันซ้ำด้วย config เดิมจะไม่ได้ค่าเริ่มต้นเดิม แม้ `meta.json` จะเขียนว่า `seed: 0` ต้องแก้ใน
  `train.py` (โค้ดของ T5) ก่อนเทรนรอบถัดไป
- `train.py` ยังไม่มีโค้ด resume: `last.pt` ถูกบันทึกทุก 4,000 iteration แต่ไม่มีที่โหลดกลับ
  ถ้าเครื่องดับกลางรัน ต้องเริ่มใหม่จาก step 0
- ทุก check ระหว่างเทรนใช้ val split ภายใน ผล test ข้างบนมาจากการประเมินแยกหลังเทรนจบ
- การประเมิน test เขียนไฟล์ลงใน folder ของ run ที่ finished แล้ว (`eval/`) โดย user `it67070295` เมื่อ 08:47
  เป็นไปตามที่ `evaluate.py` ออกแบบไว้ (entry point `python -m cloth_segment.evaluate <run>` เขียน
  `eval/eval-v1/<test_set>/metrics.json` ลง run folder และไม่เขียนทับไฟล์เดิม) ไฟล์เทรนเดิม
  (`meta.json`, `log.jsonl`, `ckpt/`) ไม่เปลี่ยน เวลาแก้ไขยังเป็น 04:36 และ 03:30
  ถ้าทีมตีความ "ไม่แก้ folder ของ run ที่จบแล้ว" ว่าห้ามเพิ่มไฟล์ด้วย ต้องตัดสินกัน แต่ไม่ใช่ความผิดของคนรัน
- ที่มาของผล test ตามที่อ่านได้จากไฟล์: `eval_commit` เป็น `7b1798b` ตรงกับ commit ของการเทรน, ใช้ `best.pt`
  step 40000 บน device `cuda` (46.1, 24.7 และ 7.2 วินาทีสำหรับ LIP, CIHP, DFMM)
  ผมไม่เห็นคำสั่งที่พิมพ์จริง (รูปแบบคำสั่งข้างบนเป็นการอนุมานจากโค้ดและ metadata) และไม่ได้รันซ้ำเพื่อตรวจว่าได้ตัวเลขเดิม
