## In plain words
All three models are trained (X2 U-Net, X3 DeepLabV3+, X4 SegFormer). M10 checks whether some weak results come from the data (labels, merged classes, object size) and not from the models.
This session added a script that breaks down each run's test predictions by raw class (the original dataset label) and by image.
First findings: LIP jumpsuits (mapped to `dress`) are predicted as upper + pants far more often than real dresses. CIHP shoes are missed mostly because they are small. CIHP socks are missed for another reason, still unknown.

## Summary
- `src/cloth_segment/rawclass.py`: three generic helpers next to the M6 `accessory` code.
  - `raw_pred_matrix(pred, raw)`: pixel counts, raw id × predicted shared class. It covers every pixel, also raw classes that map to IGNORE.
  - `shared_counts(pred, target)`: ground-truth, predicted and true-positive pixels per shared class. IGNORE is skipped, as in `evaluate.confusion_matrix`.
  - `raw_rows(matrix, dataset)`: one row per raw class present, with the shared class it maps to and how many of its pixels were predicted as that class.
- `scripts/raw_class_breakdown.py`: thin CLI over these helpers, using the M6 eval path (`raw_loader`, `iter_predictions`). For each run and test set it writes to `--out-dir`:
  - `raw_confusion.json`: per raw class, its pixels, recall and where its pixels went;
  - `per_image_shared.csv` and `per_image_raw.csv`: pixel counts per image, used for grouping by object size and for picking images to look at.
- `tests/test_rawclass.py`: 4 new tests, no GPU or real data.
- Visual review (folder added by PR #25):
  - `configs/review/m10.yaml`: runs, questions, how samples are picked, verdict codes, decision options.
  - `src/cloth_segment/review.py`: picks samples, area groups, drawing (colour overlay, outline, crop), reading and writing verdicts, tally. Tests in `tests/test_review.py` (14, no GPU or real data).
  - `scripts/review_predictions.py`: writes `data/review/M10/samples.csv` (96 images) and the predicted masks of X2–X4 for those images (`data/review/M10/pred/<alias>/<dataset>/<index>.png`).
  - `notebooks/review/m10_data_concerns.py` (marimo): questions, answered results, the 96 images with a verdict selector each, a running tally and the decisions. Input is saved at once to `docs/reports/2026-11-07-M10-verdicts.csv`.
- Nothing changes labels, splits, the eval protocol or any run folder.

## Decisions and why
- **Generic, not one script per question.** The model reports raised concerns about several classes. One breakdown of every class answers them all from one GPU pass per run, and covers classes nobody has asked about yet.
- **Cross-check against saved metrics.** The script sums its per-image counts and compares them with each run's `eval/eval-v2/<dataset>/metrics.json` (row sums, column sums, diagonal). It exits with code 1 on any mismatch. So its numbers use the same predictions as the reported metrics.
- **Output in `data/review/M10/`, not in the repo or `runs/`.** Pixel counts and predicted masks only; no image is committed (dataset licences). Finished run folders are not touched (D7). The scripts never overwrite: a different `samples.csv` stops the script, an existing mask is skipped.
- **Samples: 12 "worst" + 12 random per question.** "Worst" = lowest X4 recall among images where the class covers at least `min_share` of the image. X4 is the strongest model, so its failures are the most likely to come from the data. The random half keeps label errors from being over-counted. Seed and rule are in the config.
- **Saved predictions are checked.** Each saved mask is compared per raw class with the breakdown counts of the same run; all 288 (96 images × 3 runs) match.
- **Runs: X2, X3, X4.** These are the three runs being compared (`eval-v2`, seeded init). X1 is left out.

## Results / findings
Q5 and Q6 were checked from existing files, without the GPU. Q1 and Q2 come from the GPU pass (output of `scripts/raw_class_breakdown.py` in `data/review/M10/breakdown/`). Q3 and Q4: to be added.
Values are X2 / X3 / X4 unless a table says otherwise. "Recall" of a raw class is the share of its pixels predicted as the shared class it maps to. A raw class has no precision or IoU of its own, because a wrong prediction has no raw class.

**Q1: LIP jumpsuits are a real part of the weak LIP `dress`, but not all of it.**

| raw class (test) | maps to | pixels | recall | most of the rest goes to |
|---|---|---|---|---|
| LIP dress | dress | 7,349,016 | 0.49 / 0.55 / 0.60 | upper 0.16–0.21, background 0.10–0.12 |
| LIP jumpsuits | dress | 3,312,565 | 0.24 / 0.39 / 0.42 | pants 0.19–0.26, upper 0.19–0.24 |
| CIHP dress | dress | 17,351,843 | 0.64 / 0.68 / 0.70 | upper 0.12–0.14 |
| DFMM dress | dress | 30,180,645 | 0.90 / 0.90 / 0.91 | |
| DFMM rompers | dress | 6,522,575 | 0.93 / 0.95 / 0.95 | |

- Jumpsuits are 31% of LIP test `dress` pixels. Their recall is 0.18–0.25 lower than LIP dresses, and the missed pixels go to upper + pants. That is how CIHP labels jumpsuits (T2), so the training data teaches both answers.
- DFMM rompers are easy (0.93–0.95), so one-piece garments are not hard in general. T1 describes LIP jumpsuits as wetsuits, baseball uniforms, onesies and costumes: they look like a top and trousers.
- Real LIP dresses are also weaker than CIHP dresses (0.49–0.60 vs 0.64–0.70). Jumpsuits explain part of the LIP gap, not all of it.

**Q2: CIHP shoes are missed mostly because they are small; CIHP socks are missed for another reason.**

Recall per raw class (left and right shoe together are within 0.02 of each other):

| test set | shoes | socks | socks share of `footwear` pixels |
|---|---|---|---|
| LIP | 0.71 / 0.70 / 0.76 | 0.71 / 0.69 / 0.77 | 17% |
| CIHP | 0.55 / 0.56 / 0.67 | 0.25 / 0.32 / 0.45 | 25% |
| DFMM (footwear) | 0.91 / 0.91 / 0.93 | 0.96 / 0.94 / 0.95 | 3% (+ leggings 6%) |

Missed CIHP shoe pixels go mostly to `background` (0.23–0.33). Missed CIHP socks go to `skin` (0.16–0.29) and `pants` (0.22–0.25).

Shoe recall by shoe size, measured as the shoe pixels of an image divided by its area (X2 / X4):

| shoe area | < 0.4% | 0.4–0.8% | 0.8–1.6% | 1.6–3.2% | > 3.2% | median area |
|---|---|---|---|---|---|---|
| LIP | 0.36 / 0.40 | 0.52 / 0.57 | 0.66 / 0.72 | 0.75 / 0.80 | 0.70 / 0.75 | 2.46% |
| CIHP | 0.31 / 0.37 | 0.47 / 0.56 | 0.57 / 0.66 | 0.61 / 0.72 | 0.52 / 0.71 | 0.89% |
| DFMM | 0.64 / 0.64 | 0.76 / 0.82 | 0.91 / 0.93 | 0.96 / 0.96 | 0.93 / 0.97 | 1.19% |

Images per group, LIP / CIHP / DFMM: < 0.4%: 166 / 427 / 92; 0.4–0.8%: 249 / 414 / 207; 0.8–1.6%: 860 / 559 / 695; 1.6–3.2%: 2,315 / 344 / 259; > 3.2%: 1,605 / 80 / 21.

- Recall rises with size in all three datasets, and CIHP shoes are smaller (median 0.89% of the image vs 2.46% on LIP).
- At the same size, CIHP is still below LIP in every group: by 0.05–0.18 for X2 and 0.01–0.08 for X4. The measure is per image; CIHP images often show several people, so one person's feet are smaller than it suggests. The rest of the gap may therefore also be size.
- CIHP socks do not follow size: the largest socks are missed most (> 0.8% of the image: X2 0.23, X4 0.44, 218 images). LIP socks of the same size reach 0.70 / 0.77. One possible reason is that large CIHP "socks" are long socks or tights that look like skin or trousers. That is untested and needs a look at sample images. T1 found socks consistent across datasets from a sample; these numbers question that for CIHP.

**Q5: the X3 DFMM drops are larger than U-Net run-to-run noise.** X1 and X2 have the same config and are both scored at `best.pt` step 40000 (X1 `eval-v1`, X2 `eval-v2`). M3 changed only checkpoint selection and the `metrics.json` format; test scoring is the same in both versions, so the two can be compared. Test IoU on DFMM:

| class | X2 − X1 (noise) | X3 − X2 |
|---|---|---|
| hair | +0.0013 | −0.0124 |
| skin | +0.0005 | −0.0125 |
| footwear | −0.0005 | −0.0110 |
| headwear | +0.0078 | −0.0228 |
| skirt | −0.0040 | +0.0472 |

Except for `accessory`, |X2 − X1| is at most 0.0078 for every DFMM class. Caveat: this noise comes from one pair of U-Net runs; DeepLabV3+ may vary more between runs.

**Q6: no.** From `data/splits/splits-v2/manifest.csv` (`accessory_supply`), DFMM `accessory` has 455 train images, 57 val and 72 test (5.6% of 1,293 test images), with 157,182 test pixels (0.015% of labelled pixels). Between the two U-Net runs alone, DFMM `accessory` IoU changes by −0.207.

## Gotchas
- Both scripts need the GPU lock (`runs/.gpu.lock`) and take it themselves. Add `--wait` to queue behind another job.
- The commands, in this order:
  ```bash
  uv run python scripts/raw_class_breakdown.py \
    20261105-1307-1acb88f-unet-r34 20261105-2050-f4e2ffe-deeplabv3p-r50 \
    20261105-2220-ac9a26b-segformer-b2 --out-dir data/review/M10/breakdown
  uv run python scripts/review_predictions.py configs/review/m10.yaml
  uv run marimo edit notebooks/review/m10_data_concerns.py
  ```
- Read the per-image CSVs with `dtype={"id": str}`: CIHP ids such as `0000001` lose their leading zeros otherwise.
- X4 was trained and scored on another machine (`lemasc-ubuntu`, RTX 3060). This pass ran on `METAVERSE-05` (RTX 4070). X2 and X3 match their saved metrics exactly. X4 does not, so the script exits with code 1. Ground-truth counts are identical; at most 5,506 predicted pixels per test set differ (of 0.7–1.1 billion). The largest per-class IoU difference is 0.00044 and the mIoU difference at most 0.00006. This is GPU numeric difference, too small to change any finding here.
- Run time on the RTX 4070: X2 and X3 about 1.5 minutes each for all three test sets, X4 about 3 minutes.
- In pandas, do not read the `gt` column as `df.gt`: that is the "greater than" method. Use `df["gt"]`.
